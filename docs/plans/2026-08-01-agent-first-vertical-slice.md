# Agent-first vertical slice implementation plan

> **For Hermes:** Use the `subagent-driven-development` skill to implement this plan task by task.

**Goal:** Build one real Fluxgrade public mission that starts from the CLI, materializes a repository, runs a reactive system, accepts agent-driven deployments, injects a requirement change, evaluates the final state, and emits a replayable evidence report.

**Architecture:** The first slice uses a local Docker runtime behind the same provider contract intended for managed sandboxes. The CLI and repository are the player interface. An external evaluator container and append-only event store act as the referee. Once the loop passes real-agent playtests, replace only the provider implementation with a hosted sandbox and session gateway.

**Tech stack:** TypeScript, Node.js, pnpm workspaces, Zod, Vitest, Fastify, Docker Compose, PostgreSQL-compatible event schema, JSONL artifacts, Playwright for web regression, and the existing static trailer.

---

## Scope and acceptance test

The slice is complete when a fresh user can run:

```bash
pnpm install
pnpm build
node apps/cli/dist/index.js start checkout-latency
cd .fluxgrade-workspaces/checkout-latency-*
hermes
```

Then, through normal agent conversation, they can:

1. inspect a real unfamiliar service;
2. reproduce an incident against the running environment;
3. edit the local repository;
4. run public checks;
5. deploy through `fluxgrade deploy` without Docker or cloud credentials;
6. receive a durable midstream event in the repository;
7. adapt and redeploy;
8. submit an incident report and repository state;
9. receive an evidence-backed result generated by an external evaluator;
10. replay the sequence from recorded events.

The existing trailer and its tests must continue to pass.

## Explicitly deferred

- employer billing;
- public accounts and leaderboards;
- signed portable employment credentials;
- transcript capture;
- identity verification;
- full private deployment;
- challenge authoring UI;
- multi-region runtime placement;
- comparative hiring claims.

These are designed in `docs/ARCHITECTURE.md` but must not block validation of the agent-first loop.

### Validation gate A

Proceed to cloud hosting only if:

- all three playthroughs finish without a browser HUD;

If this gate fails, change the mission protocol before building accounts, billing, or leaderboards.

## Phase 8: Turn the proven loop into the SaaS

Build in this order after gates A and B plus the calibration prerequisites appropriate to the claim:

1. organizations, memberships, and role authorization;
2. private mission library and immutable releases;
3. employer invitation, consent, cancellation, and accommodations;
4. reviewer report and appeal workflow;
5. billing entitlements and usage metering;
6. public accounts, seasons, ratings, and rematches;
7. signed result verification;
8. SSO/SAML, SCIM, and retention controls;
9. customer-VPC runner;
10. fully private control plane only for a committed design partner.

Each capability must receive its own TDD implementation plan before code begins.

## Customer-VPC proving sequence

Before calling any deployment “private,” prove:

1. runner installation via Terraform into a fresh customer AWS account;
2. outbound-only mTLS control connection;
3. private ECR, S3, KMS, logs, and runtime placement;
4. no candidate or evaluator payload copied to the SaaS when policy forbids it;
5. explicit allowed result projection;
6. customer-controlled teardown and key revocation;
7. backup, restore, upgrade, rollback, and uninstall;
8. a threat-model review and sandbox escape test.
